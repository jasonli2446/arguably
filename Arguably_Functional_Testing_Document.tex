\section{Introduction}

This document serves as an outline of the goals for testing of the Arguably debate platform. It will describe all the functional tests for the features within the application and how we plan on implementing them. Functional testing areas include user authentication, room creation and configuration, session-based role assignment, structured turn-taking and debate flow, audience queue management, real-time moderation controls, live transcription, AI-assisted claim detection, and debate replay with analytics. The objectives of this document are to outline tests and create detailed guidelines for the functional testing plan. The other objective is to confirm that each test case verifies the software and fulfills the requirements described in our SRS document.

\section{Project and Scope}

This document presents the test cases which our team will execute so that the Arguably application can be fully tested. It will contain descriptions of how each of the use cases and functional requirements will be tested. We will test Arguably using a combination of automated tests (Jest unit tests, Playwright end-to-end tests) and manual testing for real-time WebRTC and socket.io interactions. For specific tests, reference the Test Specifications and Functional Tests sections of this document. After completing the code for each feature, we will begin to test it. Once we have finished testing that feature, we will continue to implement another section of our project.

\section{Test Design Specifications}

In this document, we will have specific tests organized by feature area as defined in the SRS. Each test will be simulated with a user input and then go through steps to get the expected output of the program. If all the steps of the program produce the correct output for the input, then the test will count as being passed. Any test that fails somewhere along the way to the final step of testing will be considered as a failed test. Tests are designed to be executable by any team member or external tester with access to the deployed application and a supported browser.

\subsection{Testing Environment and Tools}

\begin{itemize}
    \item \textbf{Browsers:} Latest two stable versions of Chrome, Firefox, Edge (Chromium), and Safari
    \item \textbf{Automated Unit Tests:} Jest with TypeScript for server actions, utility functions, and Prisma queries
    \item \textbf{End-to-End Tests:} Playwright for browser-based UI flows
    \item \textbf{Real-Time Testing:} Manual testing with multiple browser sessions for WebRTC, socket.io events, and debate flow
    \item \textbf{Database:} PostgreSQL via Supabase (test environment with seeded data)
    \item \textbf{OS:} macOS / Linux / Windows (cross-platform via browser)
    \item \textbf{Node.js:} Version 20+
\end{itemize}

\subsection{Assumptions and Special Considerations}

\begin{itemize}
    \item Users have access to the Internet, a supported web browser, camera, and microphone.
    \item At least three non-admin user accounts are active in the test environment.
    \item Supabase authentication services are available during testing.
    \item The real-time server (mediasoup SFU + socket.io) is running and accessible.
    \item WebRTC tests require two or more browser sessions (or devices) to validate peer-to-peer media flows.
    \item AI features (Live Transcription, Claim Detection) depend on external API availability (OpenAI Whisper, Gemini LLM); tests will verify graceful degradation if unavailable.
\end{itemize}

\section{Test Specifications}

\subsection{User Registration and Login}

\begin{enumerate}
    \item The user navigates to the \texttt{/auth} page.
    \item The application displays a login/signup form with fields for email and password.
    \item The user fills out the form and submits.
    \begin{itemize}
        \item If the user does not fill out a required field or provides an invalid email format, the application prevents submission and displays a validation error.
    \end{itemize}
    \item For signup: the application creates a Supabase Auth account, upserts a User record in the database via \texttt{ensureUserProfile}, and redirects the user to the browse page.
    \item For login: the application validates credentials against Supabase Auth, sets an HTTP-only JWT cookie, and redirects the user to the browse page.
\end{enumerate}

\subsection{Room Creation and Configuration}

\begin{enumerate}
    \item The authenticated user navigates to the \texttt{/create} page via the main navigation.
    \item The application displays a multi-step room creation form with fields for room name, description, debate format, turn duration, team size (if Team format), and audience elimination voting settings.
    \item The user completes the form and submits.
    \begin{itemize}
        \item If the user selects Team format, the team size field (2--5) is displayed and required.
        \item If the user enables audience elimination voting, the vote threshold percentage field is displayed.
    \end{itemize}
    \item The application creates a Session record in the database, generates a unique join code, assigns the creator as Host, and redirects to the room page at \texttt{/room/[code]}.
    \item The join code is displayed to the Host for sharing purposes.
\end{enumerate}

\subsection{Browse and Join Rooms}

\begin{enumerate}
    \item The authenticated user navigates to the \texttt{/browse} page.
    \item The application displays a list of available debate rooms with filters for format, status, and search.
    \item The user selects a room and clicks join, or enters a join code directly.
    \item The application creates a ParticipatesIn record, assigns the appropriate role (Debater if slots available, otherwise Audience), and redirects to the room page.
\end{enumerate}

\subsection{Session-Based Role Assignment}

\begin{enumerate}
    \item A user creates a room and is automatically assigned the Host/Creator role.
    \item The Host selects a participant and assigns them the Moderator role.
    \item The application updates the ParticipatesIn record and the Session's moderatorId.
    \item The assigned user's UI immediately updates to show Moderator controls without page refresh.
    \item When new users join, they are assigned Debater (if slots available) or Audience role automatically.
    \item All role transitions are logged with timestamps in the ParticipatesIn table.
\end{enumerate}

\subsection{Structured Turn-Taking and Debate Flow}

\begin{enumerate}
    \item The Moderator or Host clicks ``Start Debate'' in the room.
    \item The server-side debate engine initializes turn order based on the selected format.
    \item A countdown timer is displayed to all participants showing minutes and seconds remaining.
    \item When the timer expires, the current speaker is automatically muted, a 3-second grace period occurs, and the next speaker is unmuted.
    \item The Moderator can pause the debate (stopping all timers), resume it (with a 3-second countdown), or advance the turn manually.
    \item Visual warnings appear at 30 seconds remaining (color change) and audio warnings at 10 seconds.
    \item The debate can be ended by the Moderator, at which point all timers stop and the session status is updated.
\end{enumerate}

\subsection{Audience Queue and Dynamic Replacement}

\begin{enumerate}
    \item An audience member clicks ``Join Queue'' to enter the speaker queue.
    \item The application adds the user to the FIFO queue and displays their position.
    \item When a debater slot opens (e.g., turn ends in Expert vs. Crowd), the system automatically promotes the next queued audience member within 5 seconds.
    \item The promoted user receives a 10-second window to accept; if they decline or the window expires, they are moved to the back of the queue and the next user is promoted.
    \item If audience kick voting is enabled, audience members can vote to remove a speaker; if the configured threshold is reached, the speaker is removed and replaced from the queue.
\end{enumerate}

\subsection{Real-Time Moderation Controls}

\begin{enumerate}
    \item The Moderator sees a control panel with pause, resume, mute, kick, skip turn, extend turn, and promote controls.
    \item The Moderator clicks ``Pause'' and all debate timers immediately stop; a ``Debate Paused'' indicator is shown to all participants.
    \item The Moderator clicks ``Resume'' and a 3-second countdown appears before timers restart.
    \item The Moderator mutes a participant's microphone; the muted user cannot unmute themselves until the Moderator grants permission.
    \item The Moderator removes a participant from the room, optionally specifying a reason and ban.
    \item The Moderator extends the current turn in 30-second increments (up to 5 minutes maximum extension).
    \item The Moderator manually promotes a specific audience member to replace a debater.
    \item All moderation actions are logged with timestamps.
\end{enumerate}

\subsection{Live Transcription}

\begin{enumerate}
    \item A debate is in progress with active speakers.
    \item The real-time server streams the active speaker's audio to OpenAI Whisper.
    \item Transcribed text appears in the transcript panel within 3 seconds of speech, attributed to the correct speaker with their name and a timestamp in MM:SS format.
    \item The transcript panel auto-scrolls to show the latest content; users can scroll back to view previous content.
    \item Users can collapse or expand the transcript panel.
    \item The Moderator can correct speaker misattributions in the transcript.
\end{enumerate}

\subsection{AI-Assisted Claim Detection and Source Surfacing}

\begin{enumerate}
    \item The transcript stream is analyzed by the Gemini LLM for factual claims (statistics, studies, laws, verifiable facts).
    \item Detected claims are highlighted in the transcript within 10 seconds of the statement being transcribed.
    \item Relevant sources from reputable domains (news organizations, academic institutions, government websites) are retrieved and displayed within 15 seconds of claim detection.
    \item Sources are displayed as contextual links near the relevant claim, including the source title, URL, and a brief snippet, labeled ``AI-suggested.''
    \item Users can dismiss or report irrelevant sources.
    \item An optional claim accuracy indicator shows ``Supported,'' ``Disputed,'' or ``Unverified'' based on source analysis.
\end{enumerate}

\subsection{Debate Replay and Participation Analytics}

\begin{enumerate}
    \item After a debate ends, the system stores the recording (video, audio, transcript data) for a minimum of 30 days.
    \item Users navigate to the replay interface, which provides synchronized video and transcript playback.
    \item Users can click on transcript segments to jump to the corresponding point in the video.
    \item Playback controls include play, pause, seek, and adjustable playback speed.
    \item Role changes, eliminations, and significant events are marked on the replay timeline.
    \item The system displays per-participant analytics: total speaking time (absolute and percentage), number of turns, and average turn duration.
    \item Users can export turn and timing data as CSV.
    \item Each user's participation history shows past debates with date, topic, role, and outcome, and can be set to public or private.
\end{enumerate}
